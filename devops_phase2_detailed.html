Before you do anything else in AWS — understand IAM

IAM (Identity and Access Management) is AWS's system for controlling who can access what. Every action in AWS — launching an EC2 instance, reading an S3 file, creating a Lambda function — requires an identity with the right permissions. If you get IAM wrong, you either lock yourself out or expose your account to attackers.

The four main IAM concepts:

IAM conceptWhat it isReal-world analogy
UserA person or application with long-term credentials (username/password or access keys)A person's ID card — identifies who they are
GroupA collection of users. Policies attached to the group apply to all members.A department — all employees in "Finance" get the same access
RoleA set of permissions that can be assumed temporarily by a user, service, or account. No long-term credentials.A visitor badge — temporary access for a specific purpose
PolicyA JSON document that defines exactly what actions are allowed or denied on which resourcesA rulebook — says exactly what you're allowed to do
ANALOGY — IAM ROLES vs USERS Imagine a hospital. Users are permanent staff with ID badges they always carry. Roles are more like "on-call responsibilities" — a doctor assumes the "on-call surgeon" role during their shift, gaining temporary operating theatre access. When their shift ends, the role is dropped. AWS services (EC2, Lambda) assume Roles to access other services — they don't have permanent usernames and passwords.
IAM Policies — the JSON that defines permissions

Every IAM permission is defined in a JSON document called a Policy. The structure has three mandatory fields: Effect (Allow or Deny), Action (what AWS API calls), and Resource (which specific resources).

Example IAM policy — read-only access to a specific S3 bucket
{ "Version": "2012-10-17", // Always use this date — it's the policy language version "Statement": [ { "Sid": "AllowReadMyBucket", // Sid = Statement ID, just a label for you "Effect": "Allow", // Allow or Deny "Action": [ // What API calls are permitted "s3:GetObject", // Download files from S3 "s3:ListBucket" // List files in the bucket ], "Resource": [ // Which resources this applies to "arn:aws:s3:::my-bucket", // The bucket itself (for ListBucket) "arn:aws:s3:::my-bucket/*" // All objects inside it (for GetObject) ] } ] }
▲ The Principle of Least Privilege: Always grant the minimum permissions needed. Never use "Action": "*" or "Resource": "*" in production unless absolutely required. This is the most common IAM security mistake — over-permissive policies that give every service access to everything. The SAA-C03 exam tests this concept heavily.

What is EC2?

EC2 (Elastic Compute Cloud) is AWS's virtual machine service. When you launch an EC2 instance, you're renting a computer in an AWS data centre. You choose the operating system, the amount of CPU and RAM, and the storage. You pay by the hour (or second) only while the instance is running.

ANALOGY EC2 is like a hotel room for computers. You rent it when you need it, configure it how you want, and check out (stop the instance) when you're done. The AMI (Amazon Machine Image) is the room template — a pre-configured setup you select when checking in (like selecting "king bed, sea view" vs "single bed, city view").

AMI (Amazon Machine Image)A template containing OS + pre-installed software for launching new instancesYou can create custom AMIs from your configured instances

SAA-C03 EXAM QUESTION PATTERN
You have an EC2 instance in a private subnet. The NACL allows traffic on port 443 outbound but you cannot connect to HTTPS websites from the instance. The Security Group allows all outbound traffic. What is the most likely cause?
A) The Security Group is blocking the connection
B) The NACL does not have an inbound rule allowing the response traffic (ephemeral ports 1024-65535)
C) The instance needs an Elastic IP
D) Port 443 is not allowed in the Security Group
ANSWER: B
NACLs are stateless — you must explicitly allow BOTH the outbound request (port 443) AND the inbound response (ephemeral ports 1024–65535). Security Groups are stateful and automatically allow responses, which is why B is the answer — the NACL is blocking the return traffic.

IAM Roles for EC2 — The Secure Way to Give AWS Access
Instance profiles, why never store credentials on EC2, how roles work
Lab heavy▼
The most important IAM concept for DevOps engineers

This is critical. Never, ever hardcode AWS access keys in application code or put them on an EC2 instance. If someone accesses your instance (hacking, accidental public S3, misconfigured security group), they can steal those keys and run up a massive AWS bill or exfiltrate your data.

The correct solution: create an IAM Role with the permissions your application needs, attach it to the EC2 instance as an Instance Profile. The EC2 instance automatically receives temporary, rotating credentials through the EC2 metadata service — no keys to steal, no keys to rotate.

ANALOGY Think of a vending machine technician at a company. Instead of giving the technician a master key to every building (long-term credentials), the company gives them a temporary badge that only works on vending machine rooms and expires tonight (IAM Role). They never have a "permanent" key that can be stolen.

QUESTION 1 — IAM BASICS
A company wants to grant a contractor temporary access to their AWS account without creating a long-term IAM user. What should they use?
A) Create an IAM user with a time-limited password

QUESTION 2 — SECURITY GROUPS
An EC2 instance cannot receive SSH connections from the internet. The instance is in a public subnet with a public IP. The Security Group has an inbound rule allowing port 22 from 0.0.0.0/0. What should you check?
A) The IAM role attached to the instance
B) The NACL on the subnet — it may be blocking port 22 inbound or ephemeral ports outbound
C) The EC2 instance type — some types don't support SSH
D) CloudTrail logging
ANSWER: B — NACL
If the Security Group allows SSH (port 22), the next layer is the NACL. Remember NACLs are stateless — they need both the inbound rule (allow port 22 in) AND an outbound rule (allow ephemeral ports 1024-65535 out for the SSH response). A custom NACL that only allows port 22 inbound but blocks the response ports outbound would cause exactly this symptom.

What is S3 and how is it different from a filesystem?

S3 (Simple Storage Service) is object storage — not a filesystem. The key difference: in S3, there is no hierarchy of folders. What looks like photos/2026/january/pic.jpg is actually a single object with the key photos/2026/january/pic.jpg. The slashes are part of the key name, not real directories. This matters because S3 scales differently than a filesystem — you can store trillions of objects with no performance degradation.

ANALOGY S3 is like a massive warehouse with a flat floor (no shelves, no rooms). Each box (object) has a unique label (key). You can name labels with slashes to organize them (photos/2026/pic.jpg), but underneath it's all one giant flat space. The benefit: you can retrieve any box instantly by its label — no directory traversal, no fragmentation, no disk full errors.

S3 security — the four layers you must understand

S3 has a layered security model. Understanding the interaction between layers is critical for the SAA-C03 exam:

Block Public Access (account level) — the master safety switch. When enabled, it overrides ALL bucket policies and ACLs that would make objects public. This is what prevents data breaches from misconfigured bucket policies. Always enabled by default on new accounts.
Bucket Policy (resource-based policy) — a JSON policy attached to the bucket. Controls access for any AWS principal, external accounts, and anonymous users. This is how you make objects public (if Block Public Access is disabled).
IAM Policy (identity-based policy) — controls what AWS users/roles can do. Applied at the user/role level, not the bucket level. Both the IAM policy AND the bucket policy must allow an action for it to succeed (for cross-account access).
ACLs (Access Control Lists) — legacy, per-object. AWS recommends against using ACLs for new implementations. Bucket policies are more powerful and easier to manage.

VPC architecture — understand this before building anything in AWS

A VPC (Virtual Private Cloud) is your private section of the AWS cloud — a logically isolated network where you launch your resources. Think of it as your own private data centre inside AWS, but you control all the networking rules.

REGION: us-east-1 └─ VPC: 10.0.0.0/16 (65,534 IPs) ├─ Availability Zone: us-east-1a │ ├─ Public Subnet: 10.0.1.0/24 ← has route to Internet Gateway │ │ Resources: Load Balancer, Bastion host, NAT Gateway │ ├─ Private App Subnet: 10.0.3.0/24 ← routes outbound via NAT Gateway │ │ Resources: EC2 instances (app servers) │ └─ Private DB Subnet: 10.0.5.0/24 ← NO internet access at all │ Resources: RDS databases ├─ Availability Zone: us-east-1b ← mirror of 1a for high availability │ ├─ Public Subnet: 10.0.2.0/24 │ ├─ Private App Subnet: 10.0.4.0/24 │ └─ Private DB Subnet: 10.0.6.0/24 ├─ Internet Gateway (IGW) ← one per VPC, enables internet access for public subnets └─ NAT Gateway ← in public subnet, allows private subnets to initiate outbound internet (not inbound) Route Table: Public Subnet 10.0.0.0/16 → local (VPC internal traffic) 0.0.0.0/0 → igw-xxx (everything else goes to internet) Route Table: Private Subnet 10.0.0.0/16 → local 0.0.0.0/0 → nat-xxx (outbound internet via NAT Gateway) (NO 0.0.0.0/0 to IGW — internet cannot initiate connections in)
→ What makes a subnet public vs private? It's purely the route table. A "public subnet" is just a subnet whose route table has a route 0.0.0.0/0 → Internet Gateway. A "private subnet" has either no default route, or routes through a NAT Gateway instead. There's no magic checkbox — just a route table entry.

What is Lambda and when should you use it?

AWS Lambda runs your code in response to events without you managing any servers. You upload code, define the trigger (an S3 upload, an API call, a cron schedule, an SQS message), and Lambda handles everything else — provisioning compute, scaling, monitoring, and billing you per 100ms of execution.

ANALOGY Lambda is like a food delivery service. When an order comes in (event), the kitchen (Lambda) springs into action, prepares the food (runs your code), delivers it (returns a response), and goes idle again. You don't pay the kitchen staff when no orders come in — you only pay per delivery. Compare this to EC2: EC2 is like hiring full-time kitchen staff who are paid whether or not any orders come in.

DynamoDB — when to use NoSQL instead of SQL

DynamoDB is AWS's managed NoSQL key-value and document database. It scales automatically to millions of requests per second with single-digit millisecond latency. The tradeoff: unlike SQL databases, you must know your access patterns BEFORE designing the table.

ConceptWhat it isRule of thumb
Partition Key (Hash Key)The primary key — used to distribute data across partitions. Must be unique if no Sort Key.Choose high-cardinality values (user_id, order_id). Never use low-cardinality (status, date) — causes "hot partition"
Sort Key (Range Key)Secondary part of a composite primary key. Allows multiple items with the same partition key.Common pattern: partition_key=user_id, sort_key=timestamp — lets you query "all orders for user X sorted by time"
GSI (Global Secondary Index)An alternate index with different partition/sort key. Enables queries on non-primary key attributes.Add when you need to query by a different attribute. Costs extra — don't add GSIs you don't need.
Query vs ScanQuery uses the partition key — efficient. Scan reads every item in the table — expensive and slow at scale.NEVER use Scan in production on large tables. If you need to Scan often, add a GSI.
Provisioned vs On-Demand capacityProvisioned: specify read/write units per second (cheaper at predictable traffic). On-Demand: pay per request (better for unpredictable traffic)Start with On-Demand. Switch to Provisioned once you know your usage patterns.
EXAM QUESTION — DYNAMODB DESIGN
An e-commerce application stores orders in DynamoDB. The table has order_id as the partition key. The team needs to query "all orders placed by user X in the last 30 days" efficiently. What should they add?
A) Do a full table Scan and filter by user_id and timestamp
B) Create a Global Secondary Index with user_id as partition key and order_date as sort key
C) Migrate to RDS to support this query pattern
D) Add user_id as a Local Secondary Index
ANSWER: B — GSI with user_id (PK) + order_date (SK)
A table Scan reads every item — expensive at scale. A GSI allows querying by user_id (partition key) and filtering by order_date (sort key), using Query instead of Scan. This scales efficiently. LSI (Local Secondary Index) shares the same partition key as the table — not helpful here since we need to query by user_id, which is different from order_id.

SQS vs SNS — different tools for different problems
ServicePatternRetentionUse cases
SQS (Simple Queue Service)Pull — consumers poll the queue for messagesUp to 14 days. Messages deleted only after consumer explicitly deletes them.Work queues, task offloading, decoupling microservices, order processing
SNS (Simple Notification Service)Push — SNS pushes messages to all subscribers immediatelyNo retention — messages not delivered are lostFan-out (one event → many subscribers), alerts, mobile push notifications

The Fan-Out Pattern: SNS + SQS together. One SNS topic, multiple SQS queues subscribed to it. When an event fires, SNS delivers to all queues simultaneously. Each service processes from its own queue independently. This decouples producers from consumers completely.

Fan-out architecture example: Order placed Order Service └── publishes to → SNS Topic: order-placed ├── delivers to → SQS Queue: email-notifications │ └── consumed by → Email Lambda ├── delivers to → SQS Queue: inventory-updates │ └── consumed by → Inventory Service └── delivers to → SQS Queue: analytics └── consumed by → Analytics Service Order Service doesn't know about Email, Inventory, or Analytics. Adding a new subscriber = subscribe a new SQS queue to SNS. Zero code changes to Order Service.
EXAM QUESTION — SQS VISIBILITY TIMEOUT
An SQS consumer receives a message and starts processing it. While processing, the visibility timeout expires. The message reappears in the queue and another consumer picks it up. Now the same message is being processed twice. What is the correct solution?
A) Use a FIFO queue instead of a Standard queue
B) Make the consumer extend the visibility timeout before it expires, or set a longer initial timeout that exceeds the processing time
C) Delete the message immediately upon receipt before processing
D) Use SNS instead of SQS
ANSWER: B — Extend visibility timeout
The Visibility Timeout is how long a message is hidden from other consumers after being received. If processing takes longer than the timeout, the message becomes visible again (SQS assumes the consumer died). Solution: increase the timeout, OR have the consumer call ChangeMessageVisibility to extend it mid-processing. Option C (delete before processing) would cause data loss if the consumer crashes. Option A helps with ordering but not visibility timeout.

RTO 1 hour and RPO 15 minutes rules out Backup/Restore (RPO = time since last backup, usually hours). Multi-Site Active-Active and Warm Standby are more expensive. Pilot Light keeps core data replication running (meeting 15-min RPO) and can be scaled up within 1 hour (meeting RTO). This is the cost-optimized middle ground.
HIGH-FREQUENCY PATTERN — STORAGE SELECTION
A company needs to store 5 TB of data that is accessed once per year for compliance auditing. The retrieval time for a compliance audit can be up to 12 hours. Which storage solution is the MOST cost-effective?
A) S3 Standard
B) S3 Standard-IA
C) S3 Glacier Deep Archive
D) EBS Cold HDD (sc1)
ANSWER: C — S3 Glacier Deep Archive
Data accessed once per year with up to 12-hour retrieval = Glacier Deep Archive. It's the cheapest S3 storage class (~$0.00099/GB/month — about 95% cheaper than Standard). Retrieval takes 12–48 hours, which matches the 12-hour requirement. EBS is for block storage attached to EC2 — wrong service. Standard and Standard-IA are overkill and expensive for annual access.
HIGH-FREQUENCY PATTERN — DECOUPLING
A monolithic application processes orders synchronously. During sales events, the processing queue backs up, users see slow responses, and some orders are lost. How should the architecture be improved?
A) Scale up the database (larger RDS instance)
B) Add more EC2 instances to the Auto Scaling Group with no queue
C) Accept orders into an SQS queue immediately, confirm to the user, and process asynchronously
D) Enable ElastiCache to cache order requests
ANSWER: C — SQS queue for decoupling
The core problem is tight coupling — the frontend waits for the entire order processing to complete. By accepting the order into SQS and returning "Order received" immediately, the user gets a fast response and no orders are lost (SQS retains them up to 14 days). The processing workers drain the queue at their own pace. This is the fundamental "decoupling" pattern that AWS loves to test.
