DAY 1
The File System — Everything is a File
Inodes, hard links, symlinks, /proc filesystem
Theory + Lab▼
The big idea — understand this first

Linux treats everything as a file. Your keyboard? A file at /dev/input/event0. Your CPU temperature? A file at /sys/class/thermal/thermal_zone0/temp. Running process memory? Files in /proc/[PID]/. This is called the "everything is a file" philosophy, and it's what makes Linux so powerful for automation.

ANALOGY Think of an inode like a house address. A file's contents are the house. A hard link is another signpost pointing to the same house. A symlink is a forwarding address — it points to the signpost, not the house. If you demolish the house (delete the file), a hard link still gets you there (data intact). But a symlink leads to an empty lot (broken link).
Key concepts for today

Inode: Every file has an inode — a data structure the kernel uses to track the file's metadata (owner, permissions, timestamps, size) and which disk blocks contain the actual data. The filename is just a pointer to the inode.

Hard link: Two directory entries pointing to the same inode. Both "filenames" refer to the exact same data. Deleting one doesn't delete the data until all links are removed.

Symlink (soft link): A file that contains the path to another file. If the target is deleted, the symlink breaks. This is what /usr/bin/python3 usually is — a symlink to the actual Python binary.

DAY 2
The /proc Filesystem — Spying on the Kernel
Live kernel data without disk I/O, process inspection
Lab heavy▼
What is /proc?

/proc is a virtual filesystem. It doesn't exist on your hard drive — the Linux kernel generates its contents in memory, on demand. When you read /proc/meminfo, the kernel computes the current memory stats and hands them to you as if it were a text file. This is why tools like top, free, and ps are fast — they're just reading from /proc.

ANALOGY /proc is like a live dashboard in a car. The speedometer doesn't physically store speed on paper — it reads from a sensor and displays it in real time. Same idea: /proc files are live readings from the kernel, not stored data.

For every running process, Linux creates a directory at /proc/[PID] containing everything about that process — its command line, environment variables, open file descriptors, memory maps, and more. This is how monitoring tools work. This is how Docker reads container stats. Understanding /proc means you can monitor anything without installing special tools.

→ What is load average? It's the average number of processes either using the CPU or waiting to use it. On a single-core machine, load of 1.0 = 100% busy. On a 4-core machine, load of 4.0 = 100% busy. A load above your core count means processes are queueing.

The process state machine

Every process in Linux is always in one of these states:

ANALOGY — ZOMBIE PROCESS A zombie process is like an employee who has already quit but HR hasn't processed their exit paperwork yet. They're gone but still taking up a slot in the system. The process has died, but its entry in the process table is still there waiting for the parent to acknowledge it. If the parent never calls wait(), the zombie lingers. It doesn't use CPU or memory — but it does consume a PID slot, and if you get enough of them, you run out of PIDs.

DAY 4
Linux Signals — Talking to Processes
SIGTERM, SIGKILL, SIGHUP, signal trapping in bash
Lab heavy▼
What are signals?

Signals are the kernel's way of sending notifications to processes. When you press Ctrl+C, the kernel sends SIGINT to the process. When you run kill 1234, the kernel sends SIGTERM. The process can choose to handle (catch) most signals, or ignore them — except SIGKILL, which the kernel handles directly without asking the process.

SignalNumberDefault actionCatchable?DevOps use
SIGHUP1TerminateYesReload config without restart (nginx -s reload)
SIGINT2TerminateYesCtrl+C — interrupt a running command
SIGKILL9Terminate (immediately)NOLast resort — bypasses all handlers
SIGTERM15Terminate (gracefully)YesStandard way to stop a process — allows cleanup
SIGSTOP19Pause processNOPause a process (Ctrl+Z sends SIGTSTP, which is catchable)
ANALOGY SIGTERM is a polite tap on the shoulder: "Please finish up and stop." The process can say "just a moment" and clean up first. SIGKILL is pulling the power cord — immediate, no negotiation, no cleanup. In Kubernetes, when you delete a pod, it sends SIGTERM first and waits (the grace period), then sends SIGKILL if the process hasn't exited.

DAY 5
System Calls — How Programs Talk to the Kernel
strace, syscalls, what really happens when you run ls
Theory + Lab▼
What is a system call?

Your programs run in "user space." The kernel runs in "kernel space." These are separate security domains. When your Python script needs to write to a file, it calls write(). Python can't write directly to disk — that's a privileged operation. So Python makes a system call: it asks the kernel to do the write on its behalf.

ANALOGY Imagine a restaurant. Customers (user programs) sit at tables and order food. They can't walk into the kitchen and cook themselves — that's the kernel's domain. A system call is like giving your order to a waiter: you specify what you want, the waiter (kernel) goes to the kitchen, and comes back with the result.

The tool strace intercepts all system calls a process makes and prints them. This is incredibly useful for debugging: if a program is failing silently, strace shows you exactly what system calls it's making and which ones are failing.

kernel-stats.sh — read everything from /proc, output JSON
#!/usr/bin/env bash set -euo pipefail OUTPUT_FILE="/var/log/sys_audit.json" TIMESTAMP=$(date -u +"%Y-%m-%dT%H:%M:%SZ") # ── 1. MEMORY ────────────────────────────────────────────────────── # Read from /proc/meminfo, extract values in kB, convert to MB MEM_TOTAL_KB=$(awk '/^MemTotal:/ {print $2}' /proc/meminfo) MEM_AVAIL_KB=$(awk '/^MemAvailable:/ {print $2}' /proc/meminfo) MEM_USED_KB=$(( MEM_TOTAL_KB - MEM_AVAIL_KB )) # Calculate percentage used (bash only does integer math) MEM_PCT=$(awk -v used="$MEM_USED_KB" -v total="$MEM_TOTAL_KB" \ 'BEGIN { printf "%.1f", (used/total)*100 }') # ── 2. CPU LOAD ──────────────────────────────────────────────────── # /proc/loadavg: "1min 5min 15min running/total lastpid" LOAD_1=$(awk '{print $1}' /proc/loadavg) LOAD_5=$(awk '{print $2}' /proc/loadavg) LOAD_15=$(awk '{print $3}' /proc/loadavg) CPU_CORES=$(grep -c '^processor' /proc/cpuinfo) # ── 3. NETWORK ───────────────────────────────────────────────────── # /proc/net/dev: skip header lines, get eth0 or first real interface NET_IFACE=$(awk 'NR>2 && $1!="lo:" {sub(/:$/,"",$1); print $1; exit}' /proc/net/dev) NET_RX_BYTES=$(awk -v iface="$NET_IFACE:" '$1==iface {print $2}' /proc/net/dev) NET_TX_BYTES=$(awk -v iface="$NET_IFACE:" '$1==iface {print $10}' /proc/net/dev) # ── 4. UPTIME ────────────────────────────────────────────────────── # /proc/uptime: "uptime_seconds idle_seconds" UPTIME_SEC=$(awk '{print int($1)}' /proc/uptime) UPTIME_DAYS=$(( UPTIME_SEC / 86400 )) UPTIME_HRS=$(( (UPTIME_SEC % 86400) / 3600 )) # ── 5. OUTPUT JSON ───────────────────────────────────────────────── JSON=$(cat < { "timestamp": "$TIMESTAMP", "memory": { "total_kb": $MEM_TOTAL_KB, "used_kb": $MEM_USED_KB, "available_kb": $MEM_AVAIL_KB, "used_percent": $MEM_PCT }, "cpu": { "cores": $CPU_CORES, "load_1min": $LOAD_1, "load_5min": $LOAD_5, "load_15min": $LOAD_15 }, "network": { "interface": "$NET_IFACE", "rx_bytes": $NET_RX_BYTES, "tx_bytes": $NET_TX_BYTES }, "uptime": { "seconds": $UPTIME_SEC, "days": $UPTIME_DAYS, "hours": $UPTIME_HRS } } EOF ) # Write to log file (sudo needed for /var/log) echo "$JSON" | sudo tee "$OUTPUT_FILE" > /dev/null echo "Stats written to $OUTPUT_FILE" echo "$JSON" | python3 -m json.tool # Pretty-print for verification

File Permissions — The Binary Bitmask
chmod, chown, octal notation, special permission bits
Theory + Lab▼
How permissions actually work

Every file has three permission sets: User (owner), Group, and Other (everyone else). Each set has three bits: read (r=4), write (w=2), execute (x=1). These are added together to get an octal digit.

OctalBinaryMeaningExample use
7111rwx — read, write, executeOwner of a script directory
6110rw- — read and write onlyConfig files the owner edits
5101r-x — read and execute, no writePublic executable directories
4100r-- — read onlyShared config files, logs
0000--- — no permissionsPrivate secrets

So chmod 755 script.sh means: owner gets rwx (7), group gets r-x (5), others get r-x (5). This is the most common permission for executable files in DevOps.

The special bits go in front of the three-digit octal: SUID (4xxx), SGID (2xxx), Sticky (1xxx).

Why ACLs exist

Standard Unix permissions only support three categories: owner, group, others. But what if you need: the file owner can read/write, the devteam group can read, and one specific user (an auditor) can read-only — without adding them to devteam? Standard permissions can't do this. ACLs can.

ACLs (Access Control Lists) let you set permissions per-user and per-group, beyond the standard three-category model. They're used heavily in enterprise environments and are supported by most modern Linux filesystems (ext4, xfs, btrfs).

What is LVM and why does it matter?

Without LVM, if your disk fills up, you have a problem: you'd need to shut down, add a new disk, copy data, and restart. With LVM, you can add a new disk and expand a filesystem while it's mounted and being used — without any downtime. This is how production Linux servers handle storage growth.

ANALOGY Think of LVM like lego bricks. Physical disks are the individual bricks (Physical Volumes). You combine bricks into a pool (Volume Group). Then you carve pieces of the pool into usable storage (Logical Volumes). Adding a new brick to the pool and then extending a Logical Volume is equivalent to adding a new disk and growing the filesystem — all while the system keeps running.

The TCP 3-way handshake: Before any data is exchanged, TCP establishes a connection in three steps:

SYN — Client → Server: "I want to connect. My sequence number is X." (SYNchronize)
SYN-ACK — Server → Client: "OK, I acknowledge your sequence number X. My sequence number is Y." (SYNchronize-ACKnowledge)
ACK — Client → Server: "I acknowledge your sequence number Y. Connection established." (ACKnowledge)

This is why a TCP connection takes at least 1.5 round trips before data flows. For HTTPS, add TLS handshake on top of that. This is why reducing latency matters.

Subnetting — The Math Every DevOps Engineer Must Know
CIDR notation, binary math, subnet calculation — required for AWS VPC design
Theory + Drill▼
Why subnetting matters in DevOps

When you design a VPC (Virtual Private Cloud) in AWS, you choose CIDR blocks like 10.0.0.0/16 for the VPC and 10.0.1.0/24 for each subnet. If you don't understand what /16 and /24 mean, you'll make mistakes that cause your infrastructure to run out of IP addresses or create security holes.

ANALOGY An IP address is like a phone number. The CIDR prefix (e.g., /24) is like an area code — it says "these bits identify the network, the rest identify the specific device." A /24 means the first 24 bits are the network address. With 32 total bits, 8 bits are left for hosts = 256 addresses (254 usable, as network and broadcast are reserved).

How to calculate a subnet — step by step

Given: 192.168.10.0/26 — find the 4 subnets, their ranges, and broadcast addresses.

/26 means 26 bits for network, 6 bits for hosts. 2^6 = 64 addresses per subnet. 2^(32-26) = 64 total IPs. Usable = 62.
Block size = 256 - 192 = 64. (192 comes from the last octet of mask: 255.255.255.192). Subnets increment by 64.
Subnet 1: 192.168.10.0 → 192.168.10.63. Network: .0, Broadcast: .63, Usable: .1–.62
Subnet 2: 192.168.10.64 → 192.168.10.127. Network: .64, Broadcast: .127, Usable: .65–.126
Subnet 3: 192.168.10.128 → 192.168.10.191. Network: .128, Broadcast: .191, Usable: .129–.190
Subnet 4: 192.168.10.192 → 192.168.10.255. Network: .192, Broadcast: .255, Usable: .193–.254

DNS — How Names Become IP Addresses

Lab heavy▼
How DNS resolution works
Your computer checks /etc/hosts first (local override)
Checks local DNS cache (nscd or systemd-resolved)
Asks the recursive resolver (usually your ISP or 8.8.8.8)
Resolver asks a root nameserver ("who handles .com?")
Resolver asks the .com TLD nameserver ("who handles google.com?")
Resolver asks Google's authoritative nameserver ("what is the IP for www.google.com?")
Result is returned and cached for the duration of the TTL

TTL (Time To Live) is critical for deployments. If your DNS record has a TTL of 3600 (1 hour), and you update the IP address, clients will continue using the old IP for up to 1 hour. Before deployments, lower your TTL to 60 seconds so you can roll back quickly if needed.

Rebase vs merge — and when to use each
The difference in practice
# MERGE: preserves exact history (a merge commit is created) # Use when: merging a feature branch into main (preserves the branch history) git checkout main git merge feature/my-feature # Creates: main → ← feature commits (non-linear history) # REBASE: rewrites history (moves commits on top of main) # Use when: updating your local feature branch with latest main changes # NEVER on shared branches (it rewrites commit hashes) git checkout feature/my-feature git rebase main # Creates: main → feature commits (linear history, cleaner) # INTERACTIVE REBASE: clean up commits before pushing # Squash 3 messy "WIP" commits into one clean commit git rebase -i HEAD~3 # Opens editor: change 'pick' to 'squash' for commits to combine
COMMON BEGINNER MISTAKE Running git rebase main on a branch that's already been pushed to GitHub and shared with teammates. Rebase rewrites commit hashes. When you force-push (required after rebase), it destroys your teammates' local branches. Rule: only rebase your local branch before it's been pushed, or if you're the only one working on it.
