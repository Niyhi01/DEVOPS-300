M1 W1Linux internals — how the OS actually works
Days 1–5▼
Core concepts to internalize
The VFS (Virtual File System) — why Linux treats everything as a file. Inodes, superblocks, dentries. File descriptor limits (ulimit -n) and what happens when you hit them (EMFILE error).
Hard links vs symlinks at the inode level — what happens to each when the original file is deleted. Why Docker layers use hard links internally.
/proc and /sys virtual filesystems — how the kernel exposes live runtime data without any disk I/O. Navigate /proc/[PID]/cmdline, /proc/[PID]/fd, /proc/meminfo, /proc/net/dev.
Process state machine: R (Runnable), S (Interruptible sleep), D (Uninterruptible — disk I/O wait, unkillable), T (Stopped), Z (Zombie — finished but parent hasn't called wait()).
Kernel signals: SIGTERM(15) — catchable, graceful shutdown. SIGKILL(9) — uncatchable, kernel forcefully destroys process. SIGHUP(1) — traditionally reload config. SIGINT(2) — Ctrl+C.
System calls — how user-space requests kernel privileges: fork (clone process), execve (replace process image), waitpid (prevent zombies), open/read/write (file I/O). Use strace to watch these live.
Daily lab deliverables
DAY 1
VFS mapping. Create a file, a hard link, and a symlink. Use stat to record all three inodes. Delete the original. Document exactly what happens to each link — which is still readable and why.
DAY 2
Process tracking. Launch sleep 1000 &. Navigate to /proc/[PID]/. Dump env vars via cat /proc/[PID]/environ | tr '\0' '\n'. List all open file descriptors via /proc/[PID]/fd. Count how many FDs a sleeping process holds.
DAY 3
Zombie creation. Write a Python script that forks a child process where the parent sleeps indefinitely without calling wait(). Run ps aux | grep Z to witness the zombie flag. Kill the parent and verify the zombie is reaped by init (PID 1).
DAY 4
Signal interception. Write a bash script with trap 'echo "SIGTERM caught — cleaning up"' SIGTERM. Run it in background, send kill -15 [PID] from another terminal. Observe the catch. Then send kill -9. Document why -9 cannot be intercepted by any process.
DAY 5
Syscall analysis. Run strace -o strace.log ls /etc. Use grep -c 'openat' strace.log to count file opens. Identify which shared libraries are loaded. Write a one-page summary of what surprised you about how many syscalls a simple ls makes.
WEEK 1 CAPSTONE BUILD
Raw kernel health audit script
Build a shell script that reads raw kernel data — no top, no free, no df allowed. Parse /proc/meminfo for exact memory utilization percentages. Read /proc/loadavg for 1/5/15-minute load averages. Query /proc/net/dev for interface TX/RX bytes. Output a clean, structured JSON to /var/log/sys_audit.json. This is your first portfolio artifact — add it to GitHub.
M1 W2Permissions, storage architecture, and PAM
Days 6–10▼
Core concepts
POSIX permissions bitmask — octal arithmetic for User/Group/Other. Why 755 means what it means (binary: 111 101 101). Special bits: SUID (4000), SGID (2000), Sticky (1000). Why /usr/bin/passwd needs SUID.
ACLs — Access Control Lists beyond the standard owner/group/other model. setfacl and getfacl for fine-grained per-user permissions without changing group membership.
LVM storage stack hierarchy: Physical Volumes (PV) → Volume Groups (VG) → Logical Volumes (LV) → Filesystems. Why LVM allows live filesystem expansion without downtime — critical for production servers.
PAM (Pluggable Authentication Modules) — how Linux authentication is modular. /etc/pam.d/ configuration, password complexity enforcement, session logging.
Daily lab deliverables
DAY 6
Bitmask mastery. Set permissions using explicit octal values: chmod 4755 (SUID), chmod 2770 (SGID on directory), chmod 1777 (sticky). Test each scenario — switch users and verify the behavior matches theory.
DAY 7
Shared team directory. Create users developer_a and developer_b, group dev_team. Create /opt/shared_code with chmod 2770 so any file created inside automatically inherits the group. Prove it: write a file as developer_a, edit it as developer_b.
DAY 8
ACL precision. Grant audit_user read-only access to /opt/shared_code via setfacl -m u:audit_user:r-x without adding them to dev_team. Verify getfacl output. Then revoke access and verify again.
DAY 9
Virtual disk emulation. Create three 100MB disk images using dd if=/dev/zero of=disk1.img bs=1M count=100. Attach each as a loop device via losetup. Verify they appear as block devices in lsblk.
DAY 10
LVM build and live expansion. Initialize loop1 + loop2 as PVs. Create VG vg_production. Carve 150MB LV lv_app_data. Format as ext4, mount to /mnt/production_data. Write files to it. Then add loop3 to the VG, extend the LV to 250MB, resize the live filesystem — without unmounting. Verify files still intact.
WEEK 2 CAPSTONE BUILD
Live storage emergency simulation
Simulate a real production scenario: /mnt/production_data is at 90% capacity, a critical application is writing to it continuously. Add a new disk, extend storage live, and resize the filesystem — the application must not see a single I/O error throughout. Document every command, every output, and the total time taken. This is an SRE interview scenario.
M1 W3Enterprise networking — TCP/IP from first principles
Days 11–15▼
Core concepts
TCP 3-way handshake at the packet level (SYN → SYN-ACK → ACK). The TIME_WAIT state and why it matters for high-traffic servers (port exhaustion). TCP vs UDP tradeoffs at the application level.
Subnetting and CIDR — binary arithmetic for /24, /25, /26, /28, /30. Calculate usable hosts, network address, broadcast address without a calculator. This appears directly in AWS VPC design.
DNS resolution chain — recursive resolver → root nameserver → TLD → authoritative. TTL and what it means for zero-downtime deployments. Split-horizon DNS for internal services.
iptables/UFW — INPUT, OUTPUT, FORWARD chains. Stateful vs stateless filtering. How rules are evaluated in order. Connection tracking (-m conntrack --ctstate ESTABLISHED).
Network namespaces — how containers get isolated networking. Veth pairs, bridge interfaces. This is the exact mechanism Docker uses — you will build it by hand before Docker abstracts it.
Daily lab deliverables
DAY 11
TCP handshake capture. Run tcpdump -i any -w capture.pcap port 80. Curl a local Nginx server. Open the capture with tcpdump -r capture.pcap -A. Manually identify SYN, SYN-ACK, ACK, FIN packets by their TCP flags field.
DAY 12
Subnetting drill — 50 problems without a calculator. Given 10.0.0.0/22: total addresses, usable range, broadcast. Given 192.168.100.0/26: all four subnets, their ranges. Given a requirement for 500 hosts: what CIDR block is the smallest that fits? Time yourself — under 3 minutes per problem is the target.
DAY 13
DNS full trace. Run dig +trace cloudflare.com and document every hop: root server response, .com TLD response, authoritative NS response, final A record. Then add a fake entry to /etc/hosts and observe how it overrides DNS resolution.
DAY 14
iptables firewall. Block all incoming traffic except SSH (22) and HTTPS (443). Allow established connections out. Verify with nmap -sT localhost. Save rules via iptables-save > /etc/iptables/rules.v4 so they persist across reboots.
DAY 15
Network namespace lab — build Docker networking by hand. Create two namespaces (ip netns add ns1 ns2). Create a veth pair, assign one end to each namespace. Assign IPs (10.0.0.1/30, 10.0.0.2/30). Ping across namespaces. This is literally how Docker's bridge network works.
WEEK 3 CAPSTONE BUILD
Hardened Nginx reverse proxy — from scratch
Build a production-hardened Nginx reverse proxy with: UFW firewall (only 443 exposed), self-signed TLS certificate via openssl, proxy_pass to a local Python HTTP server, rate limiting (limit_req_zone at 10 req/s), and access log analysis. Run nmap -sV -p 1-65535 localhost — only port 443 should be reachable. Commit to GitHub with a full setup guide README including the architecture diagram.
M1 W4Bash scripting — 7 production-grade automation scripts
Days 16–20▼
Core concepts for production-grade bash
Exit codes as contracts — every script must return 0 (success) or non-zero (failure). CI/CD systems make branching decisions based on exit codes. A script that silently fails is worse than no script.
Idempotency — a script run twice should produce the same result as run once. This is the foundation of reliable automation. Test every script by running it twice.
Trap and signal handling — write scripts that clean up temp files and release locks on exit or kill. Use trap 'cleanup' EXIT SIGTERM SIGINT.
Text processing pipeline mastery: grep -E (regex), sed -i (in-place edit), awk '{print $2}' (field extraction), cut -d: -f1, sort | uniq -c | sort -rn (frequency count).
7 scripts to build — one core deliverable per day
SCRIPT 1 — system-monitor.sh
Reads CPU (/proc/stat), RAM (/proc/meminfo), disk usage per mount. Exits non-zero if any threshold is breached (configurable). Writes structured JSON alert to /var/log/monitor.json. Designed to run as a cron job every 5 minutes.
SCRIPT 2 — backup.sh
Creates tar.gz archives with timestamps. Keeps last N backups (configurable), deletes older ones. Handles SIGTERM gracefully — cleans up partial archive before exiting. Logs every action with timestamps. Idempotent: running twice doesn't create duplicate backups.
SCRIPT 3 — bulk-user-creator.sh
Reads from a CSV file (username, group, ssh_pubkey). Creates users idempotently (no failure if user already exists). Sets up home directory, adds to group, installs SSH public key, forces password change on first login. Logs every action.
SCRIPT 4 — log-analyzer.sh
Parses Nginx access log. Outputs: top 10 source IPs by request count, top 10 endpoints by request count, all 5xx errors with timestamps, requests per minute trend. Accepts log file path as argument. Exit 1 if log file not found.
SCRIPT 5 — service-watchdog.sh
Reads a list of services from a config file. Checks each with systemctl is-active. Restarts failed services. Logs every check and every restart action with timestamps. If a service fails to restart 3 times in 10 minutes, sends a critical alert (write to a special alert log file).
SCRIPT 6 — disk-sentinel.sh
Monitors all mounted filesystems via df -h. Alerts when any mount exceeds 80% (warn), 90% (critical). Write the systemd service unit file that runs this as a daemon, not a cron job — understand the difference and document why you chose one over the other.
SCRIPT 7 — security-hardener.sh
Idempotent server hardening: disables root SSH login, enforces key-only authentication, sets up UFW with minimal rules (SSH + app port only), disables unneeded services (avahi, cups, bluetooth), sets kernel parameters via sysctl (disable IP forwarding if not a router, enable SYN cookies). Running it twice must produce no changes the second time.

Core concepts

Advanced HCL concepts

Core concepts to internalize
The reconciliation loop — the controller manager constantly compares desired state (your YAML) against actual cluster state and acts on every difference. This is the core design principle of Kubernetes.

M8 W25–26GitHub Actions — 3 production pipelines
Days 211–228▼
Non-negotiable pipeline design principles
OIDC federation — GitHub Actions authenticates to AWS via OpenID Connect token (not access keys). Configure IAM Identity Provider in AWS, create an IAM role that trusts GitHub's OIDC provider. Zero stored credentials, zero rotation burden.
Artifact immutability — the Docker image built at commit SHA abc123 is the exact same image promoted to production. No rebuilding between environments. Tag images with the Git commit SHA, not latest.
Pipeline as security control — Trivy scans and OPA policy checks must block the pipeline, not just report. A pipeline that reports HIGH vulnerabilities but still deploys is not a security control.
Caching for speed — cache: npm/pip dependencies, Docker layer cache via actions/cache, Terraform plugin cache. A slow pipeline gets bypassed by developers under pressure.
Pipeline 1 — development (push to dev branch)
Trigger: push to dev branch or PR targeting dev
Steps: checkout → setup language (Node/Python) → install dependencies (cached) → run linter (eslint/flake8/shellcheck) → run tests (jest/pytest) → build Docker image (multi-stage) → Trivy scan (block on CRITICAL, warn on HIGH) → push to ECR with commit SHA tag → kubectl apply to dev namespace → run integration tests → Slack notify (success/failure)
Time target: under 8 minutes total. Optimize caching until you hit this.
Pipeline 2 — staging (push to main)
All dev steps + OPA policy check: no latest tags, no containers running as root, no images without Trivy scan
Deploy to staging namespace → smoke tests (5 core endpoints must return 200) → k6 performance test (100 VUs for 60 seconds, p99 latency < 500ms) → team Slack notification
Pipeline 3 — production (tag v*.*.*)
Trigger: push of a semver tag (v1.2.3)
Manual approval gate: an engineer must approve in GitHub before deploy begins
Canary deploy: 10% traffic to new version → wait 15 min → check error rate (auto-rollback if >1%) → 50% → wait 15 min → check → 100%
Auto-rollback: monitors Prometheus error rate metric during canary. If threshold breached, pipeline triggers a rollback deployment automatically and pages the on-call channel.
Terraform pipeline (separate workflow)
On PR: terraform plan — post the plan output as a PR comment. Reviewer must see exactly what will change before approving.
On merge to main: terraform apply -auto-approve — only for dev/staging. Production requires a separate manual workflow trigger with an explicit approval step.
Never auto-apply Terraform to production. This rule must be enforced by the pipeline, not by trust.
M8 W27–28ArgoCD GitOps — declarative, self-healing deployments
Days 229–240▼
GitOps principles
Git is the source of truth for cluster state. If it's not in Git, it doesn't exist. If it's in Git, the cluster will converge to it — automatically.
Pull-based deployment — ArgoCD polls your Git repo for changes and pulls them into the cluster. No pipeline needs kubectl access to the cluster (eliminates a major security risk).
Self-healing drift correction — if someone manually changes a resource (kubectl edit), ArgoCD detects the drift and reverts it to match Git within the sync interval.
Builds
REPO STRUCTURE
Two repos: ecommerce-app (application code) and ecommerce-gitops (Kubernetes manifests only). Structure: base/ (shared manifests), overlays/dev/, overlays/staging/, overlays/prod/ (Kustomize patches). argocd-apps/ (ApplicationSet definitions for each environment).
FULL GITOPS WORKFLOW
Developer pushes code → GitHub Actions builds image → pipeline updates the image tag in ecommerce-gitops overlays/prod/kustomization.yaml → ArgoCD detects the change (webhook or poll) → syncs to cluster → application deployed. Developer never runs kubectl. Operator never touches the cluster directly.

M9 W29–30Production observability stack

The 4 golden signals — SRE fundamentals
Latency — how long requests take. Always separate success latency from error latency (errors often return faster, masking real latency problems).
Traffic — requests per second. Baseline this so anomalies are obvious.
Errors — rate of failed requests. Track 5xx separately from 4xx (4xx is often a client issue).
Saturation — how full is your system. CPU, memory, disk I/O, queue depth, connection pool exhaustion. Usually the leading indicator before failures.
